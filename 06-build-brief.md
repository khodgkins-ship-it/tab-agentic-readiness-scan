## 1. What the prototype proves

Build the risky parts end to end. Stub the boring parts.

**In scope.** A fixture-driven pipeline producing all five artifacts from a synthetic estate, covering three findings: definition multiplicity, security exposure, and the retirement case. Plus the semantic and adoption flags those depend on.

Plus facet scoring and the interview capture schema, because both shape the data contract and retrofitting either is expensive.

**Deliberately out of scope for the prototype.** Material disagreement testing through query execution. Admin Insights extraction. The permissions sampler. Grain and freshness flags. Domain scoping beyond reading a CSV. Server support. Multi-run comparison. The guided interview subcommand and the web app capture form.

The rationale: the flagship finding depends on formula resolution, concept grouping, and usage ranking, none of which exist anywhere today and all of which can be wrong in subtle ways. Everything deferred above is well-understood API work that adds runtime without adding risk.

**Definition of done.** Against `tests/fixtures/median` with no network access, `scan` then `interview` then `score` then `report` completes and writes five artifacts to `out/`, and the web app opens from `file://` with networking disabled and renders the synthetic findings correctly.

## 2. External dependency, read this before writing code

The estate scan reuses the API client layer from an existing open source repository.

```
https://github.com/tableau/tableau-metadata-explorer
```

Clone it and read it. This is required, not optional, and the reuse plan in `05-metadata-explorer-reuse.md` was written from its documentation rather than its source, so treat that document as a starting hypothesis to verify rather than as fact.

**Read these files specifically.**

| File | Why |
|---|---|
| `tableau_rest.py` | Auth, session expiry handling, pagination. Wrap this rather than reimplementing |
| `tableau_metadata.py` | GraphQL execution. Determine whether it detects node-limit partial responses. M2 depends on the answer |
| `query_validator.py` | Schema validation. Run it over our fixed query set in CI |
| `app/static/schema/*.md` | Types, filters, and a query library generated from live introspection. This is the reference for building fixture shapes and fixed queries, since the prototype runs offline and cannot introspect |
| `orchestrator.py` | Multi-step REST and GraphQL sequencing with cross-step references |
| `router.py` | Pagination cost estimation. Informs shard sizing defaults |

**Reuse boundary.** Take the client and schema layers. Do not take the application layer. Its queries are generated by a model at request time, which is right for interactive exploration and wrong for an assessment, where findings must be reproducible across reruns and comparable across accounts.

**Vendor or depend.** Decide early and report the choice. Vendoring the two client modules into `estate_scan/clients/` keeps the prototype self-contained and avoids a Python version conflict. Depending on the repo as a package keeps upstream fixes flowing. Vendoring is the safer default for a prototype.

**Contribution candidates.** Three things belong upstream rather than in our layer, because they improve the shared tool: partial-response detection if absent, Server support if built, and the user-context function scan. Note them as you go and do not open pull requests without asking.

## 3. Environment

Python 3.9, matching the metadata explorer repo so the client layer can be vendored or imported without a version conflict. No walrus in complex expressions, no `match`, `Optional[X]` rather than `X | None`.

Dependencies kept minimal: `httpx`, `jinja2`, `openpyxl`, `pytest`. SQLite through the standard library with plain SQL, no ORM. No pandas in the prototype, since the derivation logic is clearer in explicit loops and the volumes here are fine without it.

## 5. Milestones

Work in this order. Each milestone has an acceptance test and should land as its own commit.

### M1 · Fixture generator and client interface

Build the synthetic estate generator first, because everything downstream needs it and hand-authoring fixtures does not scale.

Generate three fixtures matching the estate profiles: median at roughly 1,000 workbooks and 200 published sources, small at roughly 100 with clean lineage and few variants, and hostile which is small but full of formula edge cases.

The median fixture must contain, by construction and recorded in a `manifest.json` of expected results:

- A metric with many variants and one dominant, revenue at 47 variants with 3 covering 80 percent of views
- A metric with fewer variants and no dominant, active customer at 14 variants with 9 disagreeing
- Variants of the same metric under different names, revenue, total revenue, net rev, rev usd
- At least 20 calculated fields containing user-context functions
- Nested calculations three and four levels deep
- Roughly 70 percent of views concentrated in under 300 workbooks

Acceptance: fixtures load through `clients/fixture.py`, and the expected-results manifest is the assertion target for later milestones.

### M2 · Store and extract

SQLite schema from the build spec, including the `coverage` table. Shard planner that walks projects then object types then cursors, persists shard state, and resumes.

**Partial-response detection is the deliverable here, not a nicety.** Every GraphQL response is checked for an `errors` array and node-limit indicators. A partial response subdivides the shard and retries. Accepting truncated data silently is the tool's most dangerous failure, and `tests/test_partial.py` must force it and assert subdivision.

First, read the metadata explorer's `tableau_metadata.py` and determine whether it already detects this. Report what you find. If it does not, implement in our wrapper and note it as an upstream contribution candidate.

Acceptance: median fixture extracts fully, resumes correctly when killed mid-run, and `coverage` records every attempted measure.

### M3 · Formula resolution and normalization

Recursive resolution to base columns, scoped to the containing data source. Cycle detection, depth cap at 12, and `resolution_status` recorded as resolved, cycle, too deep, or unresolved reference. Never drop a field silently.

Normalization strips comments and whitespace, lowercases functions and identifiers, standardizes brackets and quotes, and normalizes numeric literals. It deliberately preserves filter conditions, date boundaries, and aggregation choices. When uncertain, under-normalize.

The hostile fixture drives this: cycles, deep chains, name collisions across data sources, caption references rather than field names, and unicode field names.

Acceptance: the hostile fixture resolves with every status class represented and no unhandled exception. Two formulas differing only in whitespace and alias collapse to one hash. Two differing in a date boundary do not.

### M4 · Concept grouping and ranking

Three passes with `method` and `confidence` recorded per group. Exact and normalized name match. Token and fuzzy match at a conservative threshold. Model-assisted grouping as an opt-in third pass, off by default in the prototype, with the local passes as the fallback.

Dominance rule, configurable: a variant is dominant when it carries at least 60 percent of group views and at least twice the second-ranked variant. Emit `variants_covering_80pct_views` per group.

**The tool never emits a recommended definition.** Enforce it in code. Grouping and documentation drafting are appropriate uses of a model, authoring the authoritative answer is not.

Acceptance: revenue groups to 47 variants with 3 covering 80 percent and dominance true. Active customer groups to 14 with dominance false. The four differently-named revenue variants land in one group.

### M5 · Flag engine

`rules.yaml` carrying flag id, severity, confidence class, rule expression, facet, threshold, and suppression. Engine evaluates against the store and writes to `flags`.

Prototype flag set: SEC-01, SEM-01, SEM-02, SEM-03, DF-01, DF-02, DF-03, EST-01, ADO-02. Leave the rest defined in `rules.yaml` but marked unimplemented, so the file is the complete catalog from day one.

Acceptance: thresholds change in `rules.yaml` and flag output changes with no code edit. Suppressions appear in the run log.

### M6 · Facet scoring and interview capture

From build spec sections 9 and 10. Scope to the facets the prototype's flags cover, meaning the semantic and adoption facets, and leave the rest defined in `rules.yaml` as unscored.

Build the facet band and cap syntax, both rollup rules including governance loop closure, the domain rollup with tied binding constraints, the `interview_responses` table, the YAML loader, the `INT-01` conflict flag, and the four-subcommand CLI shape.

Acceptance: a target stage of 5 on the median fixture yields readiness 2 with `semantic.singularity` as the binding constraint. Removing the target emits facet scores and no rollup. An interview response claiming a stronger score than the scan measured raises `INT-01` and does not overwrite the scan value. A test fails if `findings.json` gains a top-level score field.

### M7 · Report emit

Five artifacts. `findings.json` is the contract and the web app payload is a documented subset of it, not a parallel format.

Web app requirements: single self-contained HTML with CSS and JS inline and data embedded, fully offline with no CDN and no network calls, print stylesheet, under 5 MB, keyboard navigable, no composite score or gauge anywhere.

**Neutral severity treatment across all three findings.** Same border, same surface, no color coding at the top level. Severity appears on drill-down only. This is a decided point, not a preference to revisit.

Two builds from one run. Working carries formula text and owner names. Presentation carries counts, rankings, and disagreement figures with no formula text. Emit both, default the console output to naming the presentation build.

Acceptance: `test_report.py` asserts the presentation build contains no formula text, which is a correctness test. The app opens from `file://` with networking disabled. Print output is verified on the median and small fixtures.

## 6. Decisions already made

Do not re-open these. They are argued in the specification and reversing one quietly undoes something load-bearing.

**Fixed versioned queries, never LLM-generated at runtime.** Findings must be comparable across reruns and accounts. Record the query set version in run metadata.

**No composite maturity score, anywhere, in any artifact.** Averaging hides the binding constraint the assessment exists to find.

**Local-first.** The deterministic pass makes no external model calls. Concept grouping's model pass is opt-in per run, off by default, recorded in run metadata because it changes the confidence on every group.

**Coverage is a first-class output.** An unmeasured dimension must never read as a clean one.

**Read-only against Tableau.** Enforce in code, not convention.

**Under-normalize rather than over-normalize.** A false variant is cheap. A missed conflict is expensive.

**Sort the adjudication backlog on absence of a dominant variant, not on variant count.** Fewer variants with no clear candidate is harder than many with one.

## 7. Do not decide these alone

Flag and report rather than choosing.

**Live API field names.** Every object and field in the specification needs validation against the current schema and may differ between Cloud and Server. The prototype runs on fixtures, so this surfaces at first live run. Build the fixture shapes from the metadata explorer's `app/static/schema/*.md`, which came from live introspection, and list any field you could not confirm.

**Threshold values.** Everything in `rules.yaml` is provisional. Instrument the run to emit the distribution of variant counts and dominance ratios so thresholds can be set from real engagements later. Do not tune them against fixtures, since that calibrates to synthetic data.

**Whether the framing-light mode gets built.** An open question in the web app spec. Leave a conditional render hook and do not implement until told.
